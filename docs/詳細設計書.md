## 2. 詳細設計の前提

- 出来事の本文は必須で、最大1,000文字とする。
- 出来事の日時は登録時刻を初期値とし、`Asia/Tokyo` を基準に利用者が編集できる。
- 出来事とタグのIDはUUID文字列で生成する。
- 一覧は `occurred_at DESC, id DESC` の順で、1ページ20件固定とする。
- タグ名は前後の空白を除去したうえで、1〜30文字かつ一意とする。
- 削除は論理削除とし、削除から30日経過した記録を自動完全削除する。
- ゴミ箱では個別復元、個別完全削除、および全件削除を提供する。
- インポートの重複判定は `id` とし、既存データを優先する。
- インポートに不正行が含まれていても、正常行は登録する。
- 通常エクスポートの対象はゴミ箱を除く記録とする。
- 本番の正データはJSON/CSV、SQLiteは開発・テスト用とする。

## 4. ドメイン型・DTO

### 4.1 ドメイン型

```ts
type Timezone = 'Asia/Tokyo';

type Tag = {
  id: string;
  name: string;
  createdAt: string;
  updatedAt: string;
};

type LifeLog = {
  id: string;
  body: string;
  occurredAt: string;
  timezone: Timezone;
  tags: Tag[];
  createdAt: string;
  updatedAt: string;
  deletedAt: string | null;
};
```

### 4.2 入力型

```ts
type CreateLifeLogInput = {
  body: string;
  occurredAt?: string;
  tagIds?: string[];
  newTagNames?: string[];
};

type UpdateLifeLogInput = {
  body?: string;
  occurredAt?: string;
  tagIds?: string[];
  newTagNames?: string[];
};
```

- `occurredAt` が省略された場合は、サーバーで現在時刻を設定する。
- `tagIds` と `newTagNames` は省略時は変更なし、空配列指定時はタグをすべて外す。
- 更新入力で本文または日時を省略した場合は、既存値を維持する。
- タグの新規作成と関連付けは同一トランザクションで処理する。

### 4.3 API DTO

```ts
type LifeLogResponse = {
  id: string;
  body: string;
  occurredAt: string;
  timezone: 'Asia/Tokyo';
  tags: Array<{
    id: string;
    name: string;
  }>;
  createdAt: string;
  updatedAt: string;
};

type Pagination = {
  page: number;
  pageSize: 20;
  totalItems: number;
  totalPages: number;
};
```

- 通常APIでは `deletedAt` を返さない。
- ゴミ箱APIでは `deletedAt` を返し、削除日時を表示できるようにする。
- DBのNULLは、ドメイン上の `null` に変換する。

## 5. バリデーション設計

### 5.1 本文

| 検査 | 条件 | エラーコード |
| --- | --- | --- |
| 必須 | `body` が文字列である | `BODY_REQUIRED` |
| 空文字 | trim後の長さが1以上 | `BODY_REQUIRED` |
| 最大長 | Unicodeコードポイント数が1,000以下 | `BODY_TOO_LONG` |

- 保存値は利用者の入力を保持し、空白だけの本文は拒否する。
- エラー表示は「本文を入力してください」「本文は1,000文字以内で入力してください」とする。

### 5.2 日時

| 検査 | 条件 | エラーコード |
| --- | --- | --- |
| 形式 | ISO 8601として解釈できる | `INVALID_OCCURRED_AT` |
| タイムゾーン | `Asia/Tokyo` として正規化できる | `INVALID_TIMEZONE` |

- API受信時に日時を検証し、保存時はISO 8601文字列へ正規化する。
- 日時が存在しない場合はサーバー時刻を `Asia/Tokyo` 表記へ変換する。
- 一覧の並び替えは正規化後の日時を使用する。

### 5.3 タグ

| 検査 | 条件 | エラーコード |
| --- | --- | --- |
| 形式 | 文字列である | `INVALID_TAG_NAME` |
| 空文字 | trim後の長さが1以上 | `TAG_NAME_REQUIRED` |
| 最大長 | trim後の長さが30以下 | `TAG_NAME_TOO_LONG` |
| 重複 | 大文字・小文字を区別せず既存名と重複しない | `TAG_ALREADY_EXISTS` |

- タグ名はtrimしてから保存する。
- 同一リクエスト内の重複タグも拒否する。
- 既存タグの選択では、存在しないIDを `TAG_NOT_FOUND` として拒否する。

## 6. SQLite詳細設計

### 6.1 初期化

1. `data/` の存在を確認し、なければ作成する。
2. `data/app.db` を開く。
3. `PRAGMA foreign_keys = ON` を実行する。
4. テーブルとインデックスを `CREATE TABLE IF NOT EXISTS` で作成する。
5. スキーマバージョンを確認し、必要なマイグレーションを順番に実行する。

### 6.2 DDL

```sql
CREATE TABLE IF NOT EXISTS lifelogs (
  id TEXT PRIMARY KEY NOT NULL,
  body TEXT NOT NULL,
  occurred_at TEXT NOT NULL,
  timezone TEXT NOT NULL DEFAULT 'Asia/Tokyo',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);

CREATE TABLE IF NOT EXISTS tags (
  id TEXT PRIMARY KEY NOT NULL,
  name TEXT NOT NULL COLLATE NOCASE UNIQUE,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS lifelog_tags (
  lifelog_id TEXT NOT NULL,
  tag_id TEXT NOT NULL,
  PRIMARY KEY (lifelog_id, tag_id),
  FOREIGN KEY (lifelog_id) REFERENCES lifelogs(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_lifelogs_list
  ON lifelogs (deleted_at, occurred_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS idx_lifelogs_updated_at
  ON lifelogs (updated_at);

CREATE INDEX IF NOT EXISTS idx_lifelog_tags_tag_id
  ON lifelog_tags (tag_id, lifelog_id);
```

- `COLLATE NOCASE` により、タグ名の大文字・小文字違いを重複として扱う。
- 本文長とタグ名長はDBだけに依存せず、Domainでも検証する。
- `deleted_at IS NULL` が通常記録、値ありの場合がゴミ箱記録である。

### 6.3 Repository操作

| 操作 | SQL方針 |
| --- | --- |
| 通常一覧 | `deleted_at IS NULL`、`LIMIT 20 OFFSET (page - 1) * 20` |
| ゴミ箱一覧 | `deleted_at IS NOT NULL`、削除日時降順 |
| 登録 | `lifelogs`追加後、タグを解決して`lifelog_tags`追加 |
| 更新 | 本体を更新し、タグ指定時だけ関連を全置換 |
| 論理削除 | `deleted_at` と `updated_at` を現在時刻に更新 |
| 復元 | `deleted_at = NULL`、`updated_at`を更新 |
| 完全削除 | 対象行削除。関連行は外部キーで削除 |
| ゴミ箱全削除 | `deleted_at IS NOT NULL` の行をトランザクション内で削除 |
| 自動削除 | `deleted_at <= cutoff` の行を削除 |

- ページ番号が1未満の場合は1へ補正せず、APIで `400` を返す。
- ページを超えた場合は空の `items` と正しいページ情報を返す。
- `totalItems` と一覧取得は同一条件で実行する。

## 7. API詳細設計

### 7.1 共通レスポンス

成功時は次の形式を基本とする。

```json
{
  "item": {
    "id": "uuid",
    "body": "本文",
    "occurredAt": "2026-09-05T14:00:00+09:00",
    "timezone": "Asia/Tokyo",
    "tags": [],
    "createdAt": "2026-09-05T14:00:00+09:00",
    "updatedAt": "2026-09-05T14:00:00+09:00"
  }
}
```

エラー時は次の形式とする。

```json
{
  "error": {
    "code": "BODY_REQUIRED",
    "message": "本文を入力してください",
    "fields": {
      "body": "本文は必須です"
    }
  }
}
```

- `fields` は項目エラーがある場合だけ返す。
- サーバーログには内部エラーを記録するが、レスポンスにはスタックトレースを含めない。

### 7.2 出来事API

#### `GET /api/lifelogs`

クエリ:

| 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `page` | 整数 | 任意 | 初期値1 |
| `tagId` | UUID文字列 | 任意 | 指定タグを含む記録だけを表示 |

レスポンス:

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

#### `POST /api/lifelogs`

リクエスト:

```json
{
  "body": "出来事の本文",
  "occurredAt": "2026-09-05T14:00:00+09:00",
  "tagIds": ["uuid"],
  "newTagNames": ["新しいタグ"]
}
```

- `occurredAt` は省略可能。
- `tagIds`、`newTagNames` は省略可能。
- 成功時は `201` と登録済みの `item` を返す。

#### `GET /api/lifelogs/:id`

- 通常記録だけ取得する。
- ゴミ箱記録を指定した場合は `404` とする。

#### `PATCH /api/lifelogs/:id`

- 本文、日時、タグを指定された項目だけ更新する。
- `tagIds` または `newTagNames` が存在する場合は、タグ関連を指定内容へ置き換える。
- 成功時は `200` と更新済みの `item` を返す。

#### `DELETE /api/lifelogs/:id`

- 物理削除せず、`deleted_at` を設定する。
- 既にゴミ箱にある記録は `404` とする。
- 成功時は `204` とする。

### 7.3 ゴミ箱API

| Method | Path | 成功時 |
| --- | --- | --- |
| GET | `/api/trash?page=1` | `200`、削除日時付き一覧 |
| POST | `/api/trash/:id/restore` | `200`、復元済み記録 |
| DELETE | `/api/trash/:id` | `204`、個別完全削除 |
| DELETE | `/api/trash` | `204`、全件完全削除 |

- 個別完全削除と全件完全削除は確認操作を経て実行する。
- 復元後は通常一覧の最新位置へ再評価される。
- 30日経過データの自動削除は、Repositoryの専用処理を利用する。

### 7.4 タグAPI

| Method | Path | 内容 |
| --- | --- | --- |
| GET | `/api/tags` | 使用中・未使用を含むタグ一覧 |
| POST | `/api/tags` | タグ作成 |
| PATCH | `/api/tags/:id` | タグ名変更 |
| DELETE | `/api/tags/:id` | タグと関連付けを削除 |

- タグ削除では出来事を削除しない。
- タグ名変更時に既存名と衝突した場合は `409` を返す。

## 8. JSON/CSV詳細設計

### 8.1 JSON形式

```json
{
  "version": 1,
  "exportedAt": "2026-09-05T14:00:00+09:00",
  "items": [
    {
      "id": "uuid",
      "body": "本文",
      "occurredAt": "2026-09-05T13:30:00+09:00",
      "timezone": "Asia/Tokyo",
      "tags": ["仕事"],
      "createdAt": "2026-09-05T13:30:00+09:00",
      "updatedAt": "2026-09-05T13:30:00+09:00"
    }
  ]
}
```

- エクスポート対象は `deleted_at IS NULL` の記録だけとする。
- `version` が未対応の場合はインポートを拒否する。
- `items` が配列でない場合はファイル全体を形式エラーとする。
- `tags` はタグ名の配列として扱う。

### 8.2 CSV形式

ヘッダーは次の固定順とする。

```text
id,body,occurred_at,timezone,tags,created_at,updated_at
```

- 文字コードはUTF-8とする。
- `tags` はJSON配列文字列とする。
- RFC 4180相当の引用符、カンマ、改行を扱う。
- CSVの各行をJSON相当の入力へ変換して、同じDomain検証を通す。
- 行番号はヘッダーを1行目としてエラーに含める。

### 8.3 インポート処理

1. ファイル種別を判定する。
2. 構文を解析する。
3. 各行を入力DTOへ変換する。
4. Domain検証を行う。
5. `id` の既存データを確認する。
6. 重複を除外し、正常行を登録する。
7. 成功件数、重複件数、エラー行をレスポンスで返す。

```json
{
  "summary": {
    "total": 3,
    "imported": 1,
    "skipped": 1,
    "failed": 1
  },
  "errors": [
    {
      "row": 4,
      "code": "BODY_REQUIRED",
      "message": "本文を入力してください"
    }
  ]
}
```

- 正常行の登録は一括トランザクションとする。
- 不正行は登録せず、正常行の登録結果は維持する。
- 同一ファイル内で同じIDが複数ある場合は、最初の正常行を採用し、後続を重複として扱う。

## 9. UI詳細設計

### 9.1 メインページ状態

```ts
type LifeLogPageState = {
  items: LifeLogResponse[];
  page: number;
  totalPages: number;
  selectedTagId: string | null;
  isLoading: boolean;
  errorMessage: string | null;
  modal: { mode: 'create' } | { mode: 'edit'; id: string } | null;
};
```

- ページ変更、タグ変更、登録・編集成功時に一覧を再取得する。
- 古いリクエストの結果で新しい一覧を上書きしないよう、AbortControllerまたはリクエスト識別子を使用する。
- APIキャッシュはNext.jsのデフォルト動作に任せ、更新後はクライアント側で明示的に再取得する。

### 9.2 登録・編集モーダル状態

```ts
type LifeLogFormState = {
  body: string;
  occurredAt: string;
  selectedTagIds: string[];
  newTagName: string;
  fieldErrors: Record<string, string>;
  isSubmitting: boolean;
};
```

状態遷移:

```text
closed
  └─ open ──> editing
                 ├─ submit ──> submitting ──> success ──> closed
                 └─ submit ──> submitting ──> error ──> editing
```

- `isSubmitting` 中は保存ボタンを無効化する。
- 成功時は一覧を再取得し、モーダルを閉じる。
- 失敗時は入力値を保持してエラーを表示する。

### 9.3 タグ入力

- 既存タグはチェックボックスまたは選択リストで複数選択する。
- 新規タグは入力欄から1件ずつ追加する。
- 追加前に30文字、空文字、重複をクライアントでも検証する。
- 最終的な検証は必ずサーバー側で行う。

### 9.4 削除・完全削除

- 削除確認では「ゴミ箱へ移動します」と表示する。
- 完全削除確認では「復元できません」と明示する。
- ゴミ箱を空にする操作では対象件数を表示する。
- 自動削除された記録には通常の通知を行わず、次回ゴミ箱表示時に結果を再取得する。

## 10. 自動削除設計

### 10.1 判定

```sql
SELECT id
FROM lifelogs
WHERE deleted_at IS NOT NULL
  AND deleted_at <= :cutoff;
```

- `cutoff` は実行時刻から30日を引いた日時とする。
- 自動削除はゴミ箱対象だけに限定する。
- 物理削除前に対象件数を取得し、運用ログへ記録する。

### 10.2 実行方式

- 開発・テストでは明示的なRepository関数を呼び出して検証する。
- 本番実行方式は未決定であり、定期ジョブまたはアプリ起動時処理を候補とする。
- 同時実行時はSQLiteトランザクションで競合を防ぐ。

## 11. エラー処理

| 層 | 処理 |
| --- | --- |
| UI | 項目エラー、操作失敗、再試行導線を表示 |
| API | 入力エラーと内部エラーを形式統一して返す |
| Domain | 業務ルール違反をエラーコード付きで返す |
| Repository | SQL例外をログ可能なエラーへ変換し、トランザクションをロールバック |
| File Adapter | 構文・文字コード・行番号を含む形式エラーを返す |

- 予期しない例外を成功レスポンスへ変換しない。
- DBエラーやファイルエラーの内部パス・SQLは画面へ表示しない。
- 失敗した操作は、再試行可能な場合に再試行ボタンを提供する。

### 12.4 UIテスト

- 0件の空状態

## 13. 実装時の注意

- `better-sqlite3` をClient Componentからimportしない。
- 日時比較は文字列の見た目ではなく、正規化済みISO 8601値として扱う。
- タグの大文字・小文字の重複判定はDomainとSQLiteの両方で一貫させる。
- `id` はクライアント入力をそのまま信頼せず、形式を検証する。
- SQLは必ずプレースホルダーを使用する。
- CSVの値をHTMLとして描画しない。
- JSON/CSVの本番正データをサーバー内へ自動保存する処理は、方式決定前に実装しない。
- 既存メッセージ機能の削除時は、関連テストとREADMEの記載も同時に更新する。

## 14. 実装順序

1. Domain型、バリデーション、日時・タグの正規化を実装する。
2. SQLite接続、DDL、Repository、テスト用DB切り替えを実装する。
3. 出来事の一覧・登録・更新・論理削除APIを実装する。
4. メイン画面、一覧、登録・編集モーダルを実装する。
5. ゴミ箱、復元、個別完全削除、全件完全削除を実装する。
6. タグ管理とタグ絞り込みを実装する。
7. JSON/CSVのエクスポート・インポートを実装する。
8. 自動削除の実行方式を決定し、運用処理を実装する。
9. 既存メッセージ機能、関連API、テスト、READMEを整理する。
10. `npm test`、`npm run lint`、`npm run build` を実行する。
