## 2. 目的と方針

ライフログを登録する際に、利用者の同意を得たうえで現在地を任意に付与できるようにする。位置情報付きの記録は、本文や日時を損なわずに地図上で確認できるようにする。

方針は次のとおりとする。

- 位置情報は任意項目とし、従来どおり位置情報なしでも登録できる。
- 位置情報の取得はブラウザの Geolocation API を利用し、取得前に利用者へ目的を明示する。
- サーバーには緯度・経度と取得時点の精度を保存する。端末の生の位置履歴や継続追跡は扱わない。
- 地図ライブラリとタイル提供元をアプリのドメインロジックから分離する。
- 逆ジオコーディングによる住所表示は初回実装の必須要件にせず、外部サービスの選定後に追加できる構造にする。
- 既存データと既存 API のレスポンス互換性を維持する。

## 3. 対象範囲

### 3.1 対象

- 記録の新規登録時に現在地を取得して付与する操作
- 編集時の位置情報の追加、再取得、削除
- 記録一覧で位置情報の有無を確認する表示
- 位置情報付き記録を地図上にマーカー表示する画面
- マーカーから該当記録を確認し、記録詳細または一覧へ移動する操作
- 位置情報の入力値検証、取得失敗時の通知、保存・削除
- 位置情報を含むデータのエクスポート・インポート拡張

### 3.2 対象外

- バックグラウンドでの継続的な位置追跡
- 移動経路、速度、滞在時間の自動推定
- 位置情報の第三者共有、公開プロフィール、複数ユーザー間共有
- 位置情報からの自動タグ付け
- 住所を正規化して保存すること
- 地図上での新規地点指定による記録作成
- 逆ジオコーディングの導入（別設計で決定する）

## 4. 利用シナリオ

### 4.1 位置情報を付けて記録する

1. 利用者が「記録する」を選択する。
2. モーダル内の「現在地を追加」を選択する。
3. 位置情報を利用する目的と、ブラウザの許可が必要であることを表示する。
4. 許可後、取得した緯度・経度・精度を確認できる状態にする。
5. 利用者が本文・日時とともに保存する。

取得した位置情報は、取得できた時点で自動保存せず、記録の保存操作が完了したときだけサーバーへ送信する。

### 4.2 位置情報を編集・削除する

- 編集モーダルに現在の位置情報の有無と取得精度を表示する。
- 「現在地を更新」で再取得し、保存前はプレビュー状態にする。
- 「位置情報を削除」で保存対象から外す。
- 編集をキャンセルした場合、再取得・削除の変更は保存しない。

### 4.3 地図で振り返る

- `/map` を地図表示画面とする。
- 初期表示は、削除されていない位置情報付き記録を取得して表示する。
- 初期中心は位置情報付きの直近の記録とし、初期ズームはその記録を確認しやすい市街地レベルにする。位置情報付き記録がない場合は、日本全体が収まる範囲を表示する。
- マーカー選択時に日時、本文の先頭、タグをポップアップ表示する。
- ポップアップから記録一覧の該当ページまたは詳細表示へ遷移できる。
- 同一地点の記録が多い場合は、マーカーのクラスタリングまたは件数表示で重なりを抑制する。

## 5. データモデル

### 5.1 LifeLog への追加項目

既存の `LifeLog` に次の nullable なフィールドを追加する。

```ts
type LifeLogLocation = {
  latitude: number;
  longitude: number;
  accuracyMeters: number | null;
  capturedAt: string;
};

type LifeLog = {
  // 既存フィールド
  location: LifeLogLocation | null;
};
```

- `latitude` は -90 以上 90 以下、`longitude` は -180 以上 180 以下とする。
- `accuracyMeters` は 0 より大きい値、または `null` とする。ブラウザが返さない場合は `null` にする。
- `capturedAt` は位置情報を取得した時刻で、ISO 8601形式で保存する。
- `capturedAt` は `occurredAt` と別管理にする。後から日時を編集しても、位置を取得した時点を失わないようにする。
- 高度、方位、速度は初回実装では保存しない。

### 5.2 SQLite

既存の `lifelogs` テーブルへ次の nullable カラムを追加する。既存データの値はすべて `NULL` とする。

```sql
ALTER TABLE lifelogs ADD COLUMN latitude REAL;
ALTER TABLE lifelogs ADD COLUMN longitude REAL;
ALTER TABLE lifelogs ADD COLUMN location_accuracy_meters REAL;
ALTER TABLE lifelogs ADD COLUMN location_captured_at TEXT;
```

データベース初期化処理は、既存テーブルにカラムがない場合だけマイグレーションを実行できるようにする。単純な `CREATE TABLE IF NOT EXISTS` だけでは既存 DB に反映されないため、`PRAGMA table_info(lifelogs)` で存在確認を行う。

位置情報付きの地図取得を高速化する必要が生じた場合に備え、次のインデックスを追加候補とする。

```sql
CREATE INDEX IF NOT EXISTS idx_lifelogs_location
  ON lifelogs (deleted_at, latitude, longitude);
```

初回は一覧取得の件数が少ないため、実測で必要性を確認してから追加する。

### 5.3 入出力 DTO

登録・更新入力に次を追加する。

```ts
type LifeLogLocationInput = {
  latitude: number;
  longitude: number;
  accuracyMeters?: number | null;
  capturedAt: string;
} | null;

type CreateLifeLogInput = {
  // 既存フィールド
  location?: LifeLogLocationInput;
};
```

API レスポンスには `location: null` または上記オブジェクトを常に含める。クライアント側の分岐を単純化し、将来の必須化による破壊的変更を避ける。

## 6. API 設計

### 6.1 既存 API の拡張

`POST /api/lifelogs` と `PATCH /api/lifelogs/:id` の入力・出力に `location` を追加する。

- `location` を省略した登録は `null` として扱う。
- 更新で `location: null` を受け取った場合は既存位置を削除する。
- 更新で `location` を省略した場合は既存位置を維持する。
- バリデーションエラーは既存の形式に合わせて HTTP 400 を返す。
- 緯度・経度の範囲外、必須項目の欠落、日時の不正、精度の負数は保存しない。

### 6.2 地図用 API

`GET /api/lifelogs/map` を追加する。

クエリパラメータ:

| パラメータ | 必須 | 説明 |
| --- | --- | --- |
| `from` | 任意 | `occurredAt` の開始日時 |
| `to` | 任意 | `occurredAt` の終了日時 |
| `tagId` | 任意 | タグによる絞り込み |

レスポンス例:

```json
{
  "items": [
    {
      "id": "uuid",
      "occurredAt": "2026-09-05T10:00:00.000Z",
      "bodyPreview": "記録本文の先頭...",
      "tags": [],
      "location": {
        "latitude": 35.681236,
        "longitude": 139.767125,
        "accuracyMeters": 12.5,
        "capturedAt": "2026-09-05T10:01:00.000Z"
      }
    }
  ]
}
```

- `deleted_at IS NULL` かつ `latitude IS NOT NULL` の記録だけを返す。
- 地図画面に不要な全文本文は返さず、表示用の短い `bodyPreview` を返す。
- 初回は `occurredAt DESC, id DESC` の順で最大100件を取得する。
- 100件を超えた場合は API が `truncated: true` を返し、画面上で表示対象が上限に達していることを通知する。
- 期間指定、表示範囲（bounding box）、クラスタリング用集約は後続拡張とする。

## 7. UI・コンポーネント設計

### 7.1 コンポーネント

```text
src/app/
  map/
    page.tsx                 # 地図画面（サーバー側の入口）
  components/
    LocationPicker.tsx       # 位置情報の取得・確認・削除
    LifeLogMap.tsx           # 地図ライブラリを包むクライアントコンポーネント
    MapMarkerPopup.tsx       # マーカーの記録概要
```

- Geolocation API と地図ライブラリはクライアントコンポーネントに閉じ込める。
- `page.tsx` や Route Handler は、位置情報取得のブラウザ API に依存しない。
- 地図ライブラリ固有の型やイベントを `LifeLogMap` の外へ漏らさない。

### 7.2 記録モーダル

- 位置情報なしを初期状態とする。
- 「現在地を追加」「現在地を更新」「位置情報を削除」を明確に分ける。
- 取得中はボタンを無効化し、「位置情報を取得しています」と表示する。
- 取得成功時は緯度・経度を丸めた表示と精度を表示する。保存値は丸めない。
- 取得失敗時は、権限拒否・タイムアウト・利用不可を区別して案内する。
- 権限拒否でも本文だけの登録を継続できる。

### 7.3 地図ライブラリとタイル

地図ライブラリは Leaflet + React-Leaflet を採用する。React のライフサイクルとの統合は `LifeLogMap` に限定し、将来的に別ライブラリへ差し替えられるようにする。地図表示は初回実装で必要なマーカー、ポップアップ、表示範囲変更を満たせるため、MapLibre GL JS の高度な描画機能は現時点では採用しない。

タイル提供元は OpenStreetMap の標準タイルを採用する。ただし、小規模な個人利用に限定し、実装前に公式の利用ポリシー、レート制限、帰属表示の要件を確認する。タイル URL は環境設定から差し替え可能にし、アクセス量が増えた場合や利用条件に抵触する場合は、正式なタイルプロバイダーまたは契約済みプロバイダーへ移行する。地図上には必須の OpenStreetMap 帰属表示を常に表示する。

## 8. 位置情報取得・エラー処理

`navigator.geolocation.getCurrentPosition` を使い、次の設定を基本とする。

- `enableHighAccuracy: true`
- `timeout: 10_000`
- `maximumAge: 300_000`

高精度取得が失敗しても低精度で自動再試行せず、利用者がボタンを押した場合だけ再取得する。エラーを握りつぶさず、次の分類で利用者へ通知する。

| 状況 | 通知 | 保存 |
| --- | --- | --- |
| 権限拒否 | ブラウザ設定で許可できることを案内 | 位置なしで継続可能 |
| 取得タイムアウト | 屋内・電波状況を確認して再試行できる | 位置なしで継続可能 |
| 端末が非対応 | 対応ブラウザ・端末ではないことを案内 | 位置なしで継続可能 |
| API/DB 保存失敗 | 保存に失敗したことを通知し再送信可能にする | 不完全保存しない |

HTTPS（localhost を除く）でのみ位置情報を利用できることを、実行環境の前提およびドキュメントに明記する。

## 9. プライバシー・セキュリティ

- 位置情報は個人情報に準じて扱い、ログ、エラーメッセージ、分析イベントへ緯度・経度を出力しない。
- 位置情報を利用する目的、保存対象、削除方法を UI で明示する。
- ブラウザ権限の状態をアプリ側で勝手に再要求しない。利用者の操作を起点に取得する。
- 位置情報付き API は将来認証を導入する場合に認証境界へ含める。
- API はクライアント入力を信頼せず、サーバー側でも数値、範囲、精度、日時を検証する。
- `Permissions-Policy` の `geolocation=()` を、アプリ自身の必要な範囲だけ許可する設定へ変更する。第三者 iframe へは許可しない。
- 地図タイルへのアクセスで、位置情報が外部サービスへ送信される可能性を利用者へ説明する。タイル URL と送信内容を確認したうえで採用する。
- エクスポートファイルに位置情報が含まれることを明示し、ダウンロード後の取り扱いに注意を促す。

## 10. エクスポート・インポート

- 既存 JSON の各記録へ `location` を追加する。
- `location` がない旧形式は `null` として読み込む。
- 不正な位置情報を含む行は既存のインポート方針に従ってエラーとして扱い、他の正常行の処理を妨げない。
- インポート時は `id` の重複判定を維持し、既存記録を優先する。
- 緯度・経度・精度・取得日時はインポート時にも同じドメイン検証を通す。

## 11. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 性能 | 地図初期表示を、位置情報付き記録100件で通常操作可能な時間に収める |
| レスポンシブ | スマートフォンでは地図と記録概要を縦方向、PCでは地図と一覧を並列表示できる |
| 可用性 | 地図が読み込めない場合も本文一覧と記録操作は利用できる |
| アクセシビリティ | 地図操作に依存しない記録一覧への導線と、マーカー内容のテキスト表示を提供する |
| プライバシー | 位置情報を持たない記録の動作・表示を従来から変更しない |

## 12. テスト方針

### 12.1 ドメイン・リポジトリ

- 緯度・経度の境界値と範囲外を検証する。
- 精度の `null`、正数、0、負数を検証する。
- 位置情報なしの既存記録が取得できることを検証する。
- 位置情報付き記録の登録・更新・削除・論理削除後の地図取得を検証する。
- 既存 DB に対するカラム追加マイグレーションを検証する。

### 12.2 API

- `location` 省略、`null`、正常値、異常値の HTTP 応答を検証する。
- 地図 API が削除済み記録と位置情報なし記録を除外することを検証する。
- 期間・タグ絞り込みと、本文プレビューの長さ・内容を検証する。

### 12.3 UI

- Geolocation API の成功、権限拒否、タイムアウトをモックして確認する。
- 取得した位置情報が保存前にプレビューされ、キャンセルで破棄されることを確認する。
- 地図ライブラリのロード失敗時もエラー表示と一覧導線が残ることを確認する。
- マーカー選択時に記録概要が表示されることを確認する。

## 13. 段階的な実装手順

1. ドメイン型、入力検証、SQLite マイグレーションを追加する。
2. 既存の登録・編集 API とリポジトリを位置情報対応にする。
3. 記録モーダルへ `LocationPicker` を追加する。
4. `GET /api/lifelogs/map` と地図画面を追加する。
5. エクスポート・インポート、権限ポリシー、利用者向け説明を更新する。
6. 実機・主要ブラウザで権限、HTTPS、地図タイル、モバイル表示を確認する。

各段階で既存の位置情報なしの登録・一覧・編集・削除が動作することを受け入れ条件とする。
