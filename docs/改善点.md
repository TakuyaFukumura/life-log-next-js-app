# リポジトリ改善点

調査日: 2026-09-06
対象: `main` 時点のアプリケーションコード、テスト、CI、README

## 概要

現状は、個人利用向けのライフログ登録・地図表示・ゴミ箱・JSON入出力という主要機能が整理されており、入力検証、SQLiteの外部キー、CIでの lint・build・test も整備されています。

一方で、公開運用へ進む場合に、**認証・認可がないこと**と**SQLiteファイルの保存方式が実行環境に依存すること**が大きなリスクになります。また、インポートや一覧取得の規模が大きくなったときの入力制限・クエリ効率・画面状態の扱いにも改善余地があります。

## 優先度

| 優先度 | 意味 |
| --- | --- |
| P0 | 公開前に対応すべき。データ漏えい・データ消失・サービス停止につながる |
| P1 | 早期に対応すべき。運用規模や異常入力で不具合・性能劣化が発生しうる |
| P2 | 品質・保守性を高める改善。機能拡張前に対応すると効果が大きい |

## P0: 公開前に対応すべき項目

### 1. 認証・認可とCSRF対策を追加する

- **根拠**: `src/app/api/lifelogs/route.ts`、`src/app/api/lifelogs/[id]/route.ts`、`src/app/api/trash/route.ts` などのAPIに、利用者を識別する処理がない。
- **影響**: アプリをインターネットへ公開すると、URLを知っている第三者が全記録の取得、作成、論理削除、復元、完全削除、エクスポートを実行できる。ライフログには本文と位置情報が含まれるため、機密性への影響が大きい。
- **改善案**: まず単一ユーザー運用なら、認証済みセッションまたは短命トークンを全APIで必須にする。複数ユーザー化する場合は、`user_id` を各データに追加し、すべてのSELECT/UPDATE/DELETEを所有者条件付きにする。Cookie認証を採用する場合は、Origin/Referer検証またはCSRFトークンも導入する。認証なしで使う構成を残す場合は、READMEに「ローカル専用」と明記し、公開デプロイをサポート対象外にする。

### 2. SQLiteの永続化方式とデプロイ先を見直す

- **根拠**: `lib/database.ts:27-43` で `process.cwd()/data/app.db` を直接開き、`src/app/api/*` から書き込みを行っている。`vercel.json` はVercelへのデプロイ設定だが、永続データストアの設定はない。
- **影響**: 一般的なサーバーレス実行環境では、ローカルファイルはインスタンス間で共有されず、再デプロイ・インスタンス破棄・スケールアウトでデータが消失または分岐する。複数インスタンスからSQLiteへ書き込む構成も安全ではない。
- **改善案**: 本番はPostgreSQL等の永続DBへ移行し、接続プール、スキーママイグレーション、バックアップ、復旧手順を用意する。SQLiteを継続するなら、永続ボリュームを持つ単一ホストに限定し、`DATABASE_PATH` を環境変数化して起動時に書き込み可否を検証する。どちらの場合も、JSONエクスポートだけに依存しない定期バックアップを追加する。

## P1: 早期に対応すべき項目

### 4. 日時とタイムゾーンの扱いを明確にする

- **根拠**: `lib/lifelog/repository.ts` では `timezone: 'Asia/Tokyo'` を固定している一方、`src/app/logs/page.tsx` ではブラウザのローカル日時を `toISOString()` に変換して送信している。
- **影響**: 日本国外の環境で入力した日時が、表示上の意図と保存された `Asia/Tokyo` の意味でずれる可能性がある。DSTのある地域では特に再現しやすい。
- **改善案**: 「常に日本時間で入力する」のか「利用者のタイムゾーンで入力する」のかを仕様化する。後者なら保存時にUTCとIANAタイムゾーンを別々に持ち、表示時に利用者のタイムゾーンへ変換する。前者なら入力欄・README・API仕様で日本時間固定を明示し、ブラウザのタイムゾーンに依存しない変換を実装する。

## P2: 品質・保守性の改善

### 5. CRUD・ゴミ箱・地図APIのテストを拡充する

- **根拠**: 現在のAPIテストは主にエクスポートとインポート（`__tests__/src/app/api/lifelogs/export/route.test.ts`、`__tests__/src/app/api/lifelogs/import/route.test.ts`）で、登録・更新・削除・復元・完全削除・地図APIの異常系を直接カバーしていない。
- **影響**: 重要なデータ操作の回帰をCIで検出できない。特に論理削除、復元、タグ関連、位置情報の境界値は、UI操作だけでは不具合を見つけにくい。
- **改善案**: リポジトリ層の統合テストを中心に、CRUD、タグの重複・未知ID、ページ境界、論理削除後の一覧除外、復元、完全削除、位置情報の範囲、期間フィルタを追加する。API層では不正JSON、異常なページ、内部エラー、認証エラーのレスポンスを検証する。

### 6. 非同期操作中の二重送信と競合更新を防ぐ

- **根拠**: `src/app/logs/page.tsx` と `src/app/trash/page.tsx` の保存・削除・復元ボタンは、リクエスト中の状態に応じた一貫した無効化がない。`fetchItems` の再実行も可能で、古いレスポンスが新しい状態を上書きしうる。
- **影響**: 保存や削除の連打による重複リクエスト、一覧の表示順の一時的な逆転、ユーザーが処理完了を判断できない状態が発生する。
- **改善案**: 画面ごとに操作中フラグを設けて対象ボタンを無効化し、保存・削除処理を共通のAPIクライアントへ切り出す。AbortControllerまたはリクエスト連番で古い一覧取得結果を破棄し、成功・失敗・再試行の状態を明確に表示する。

### 7. CSVシード処理をCSVとして正しく解析する

- **根拠**: `lib/database.ts:7-23` は改行で分割して各行をそのままタグ名として扱っており、CSVの引用符・カンマ・エスケープを解釈していない。
- **影響**: タグ名にカンマや引用符を含めたい場合に壊れる。また、空行を単純に除去するため、入力ファイルの形式エラーを正確に検出できない。
- **改善案**: タグ名の仕様を英数字・日本語のみなどに制限するなら明記して検証する。一般的なCSVを受け付けるならCSVパーサーを使い、ヘッダー、列数、重複、空白の扱いを検証する。起動時のシード失敗を分かりやすくログへ出す。

### 8. スキーマ変更を明示的なマイグレーションで管理する

- **根拠**: `lib/database.ts:51-65` はテーブル作成後に `PRAGMA table_info` を確認し、未存在の位置情報カラムを都度 `ALTER TABLE` している。スキーマのバージョン番号やマイグレーション履歴はない。
- **影響**: 今後の変更が増えると、適用順序・失敗時の復旧・既存DBとの互換性を追跡しにくい。複数プロセスが同時起動した際の初期化競合も管理しづらい。
- **改善案**: `schema_migrations` 等でバージョンを管理し、各マイグレーションを順番にトランザクション適用する。アプリ起動時の自動変更を続ける場合も、変更内容とロールバック方針をリポジトリに残す。

## 推奨する着手順

1. 公開範囲を決め、認証・認可とCSRF対策を追加する。
2. 本番の永続DB・バックアップ・復旧方針を決める。Vercelで運用するならSQLiteを本番データストアにしない。
3. CRUD・ゴミ箱・地図APIの統合テストを追加する。
4. 日時仕様、画面の二重送信、CSV/マイグレーションを順に改善する。
