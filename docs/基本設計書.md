## 2. 基本方針

- 日々の出来事を複数件記録し、新しい順に振り返れる構成とする。
- 本番運用ではJSONを正データとし、SQLiteは開発・テスト用の保存先に限定する。
- 画面はSQLiteのテーブル構造を直接扱わず、ドメインモデルとAPIを介してデータを扱う。
- 登録・編集は一覧画面からモーダルで行う。
- 削除は論理削除とし、ゴミ箱から復元または完全削除できるようにする。
- 個人利用を前提とし、初期版ではログイン・共有・複数ユーザー対応を行わない。
- 日時は日本時間（`Asia/Tokyo`）を基準とする。
- 初期実装は出来事の登録、一覧、編集、論理削除を優先し、その後にタグ、ゴミ箱、入出力を追加する。

## 3. システム構成

### 3.1 技術構成

| 層 | 採用技術・方針 |
| --- | --- |
| 実行基盤 | Node.js |
| Webフレームワーク | Next.js 16 / App Router |
| UI | React 19、TypeScript |
| スタイリング | Tailwind CSS |
| API | Next.js Route Handlers |
| DB | SQLite（開発・テスト用） |
| DBドライバ | `better-sqlite3` |
| テスト | Jest、React Testing Library |
| 静的解析 | ESLint |

### 3.2 論理構成

```text
ブラウザ
  └─ React画面
       ├─ 一覧・ページング・タグ絞り込み
       ├─ 登録/編集モーダル
       └─ ゴミ箱・タグ管理・入出力操作
              │ fetch
              ▼
       Next.js Route Handlers
              │
              ▼
       Domain / Validation
              │
              ▼
       Repository
              │
              ▼
       SQLite（開発・テスト時）／JSON（本番の正データ）
```

- Reactコンポーネントは入力・表示状態を管理する。
- Route HandlerはHTTP入出力とステータスコードを管理する。
- ドメイン層は文字数、日時、タグなどの業務ルールを検証する。
- RepositoryはSQLとSQLite接続を担当する。
- `better-sqlite3` はサーバー側コードからのみ利用し、クライアントバンドルへ含めない。

既存の `lib/database.ts` は出来事機能の開発・テスト用SQLite接続へ整理する。既存のメッセージAPIとメッセージ表示機能は、出来事機能への移行時に削除する。

## 4. ドメイン設計

### 4.1 出来事モデル

```ts
type LifeLog = {
  id: string;
  body: string;
  occurredAt: string;
  timezone: 'Asia/Tokyo';
  tags: Tag[];
  createdAt: string;
  updatedAt: string;
  deletedAt: string | null;
};
```

- APIとアプリ内部ではキャメルケースを使用する。
- DBではスネークケースを使用し、Repositoryで相互変換する。
- 日時はISO 8601形式で保持し、`occurredAt` は日本時間として解釈・表示する。
- `body` は前後の空白を検証時に扱うが、保存時に利用者の本文を意図せず改変しない。

### 4.2 タグモデル

```ts
type Tag = {
  id: string;
  name: string;
  createdAt: string;
  updatedAt: string;
};
```

- タグ名は正規化後に空文字でなく、30文字以内かつ重複しないことを検証する。
- 1件の出来事にタグを0個以上付与できる。
- タグ削除時は中間テーブルの関連だけを削除し、出来事は残す。

## 5. データベース設計

### 5.1 DBファイル

- 開発・テスト時のDBファイルは `data/app.db` とする。
- 本番環境ではSQLiteを永続化の正データとして扱わず、JSONを正データとして扱う。
- 本番の初期データはリポジトリ内の `data/lifelogs.json` から読み込む。
- 本番でアップロードしたデータは実行中だけ反映し、再起動時は初期JSONへ戻る。
- 本番のアップロードはJSONのみとし、既存データへマージする。
- 本番のダウンロードは画面上の変更を反映したJSONのみとする。
- `data/` が存在しない場合は初期化処理で作成する。
- DB接続はプロセス内で再利用し、リクエストごとに接続を作り直さない。
- DB初期化や接続失敗は、利用者向けエラーとして通知できる形で上位へ返す。

### 5.2 テーブル

#### `lifelogs`

| カラム | SQLite型 | 制約・説明 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY。アプリ側でUUIDを生成する |
| `body` | TEXT | NOT NULL。最大1,000文字 |
| `occurred_at` | TEXT | NOT NULL。ISO 8601日時 |
| `timezone` | TEXT | NOT NULL。初期値 `Asia/Tokyo` |
| `created_at` | TEXT | NOT NULL |
| `updated_at` | TEXT | NOT NULL |
| `deleted_at` | TEXT | NULL。値があればゴミ箱状態 |

インデックス:

- `(deleted_at, occurred_at DESC, id DESC)`：通常一覧とゴミ箱一覧
- `updated_at`：更新順の取得や運用確認

#### `tags`

| カラム | SQLite型 | 制約・説明 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY |
| `name` | TEXT | NOT NULL、UNIQUE |
| `created_at` | TEXT | NOT NULL |
| `updated_at` | TEXT | NOT NULL |

#### `lifelog_tags`

| カラム | SQLite型 | 制約・説明 |
| --- | --- | --- |
| `lifelog_id` | TEXT | `lifelogs.id`への外部キー |
| `tag_id` | TEXT | `tags.id`への外部キー |

- PRIMARY KEYは `(lifelog_id, tag_id)` とする。
- 関連削除は `ON DELETE CASCADE` とする。
- SQLiteの外部キー制約を接続時に有効化する。

### 5.3 トランザクション

次の操作は1トランザクションで処理する。

- 出来事の登録とタグ関連付け
- 出来事の更新とタグ関連付けの差し替え
- 出来事の復元・完全削除
- タグ削除と関連付けの削除
- 複数件のインポート

途中で失敗した場合は、出来事本体とタグ関連の片方だけが更新された状態を残さない。

## 6. API設計

### 6.1 共通方針

- JSON APIの日時・識別子・タグ形式はドメインモデルに合わせる。
- 成功時は操作結果または対象データを返す。
- 入力不正は `400`、対象なしは `404`、DB障害は `500` を基本とする。
- エラー形式は次で統一する。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "本文を入力してください",
    "fields": {
      "body": "本文は必須です"
    }
  }
}
```

### 6.2 エンドポイント

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/api/lifelogs?page=1&pageSize=20&tagId=` | 通常一覧、ページング、タグ絞り込み |
| POST | `/api/lifelogs` | 出来事の登録 |
| GET | `/api/lifelogs/:id` | 出来事の取得 |
| PATCH | `/api/lifelogs/:id` | 本文・日時・タグの更新 |
| DELETE | `/api/lifelogs/:id` | ゴミ箱への移動 |
| GET | `/api/trash?page=1&pageSize=20` | ゴミ箱一覧 |
| POST | `/api/trash/:id/restore` | 記録の復元 |
| DELETE | `/api/trash/:id` | 記録の完全削除 |
| DELETE | `/api/trash` | ゴミ箱を空にする |
| GET | `/api/tags` | タグ一覧 |
| POST | `/api/tags` | タグ作成 |
| PATCH | `/api/tags/:id` | タグ名変更 |
| DELETE | `/api/tags/:id` | タグ削除 |
| GET | `/api/export?format=json` | JSON/CSVエクスポート |
| POST | `/api/import` | JSON/CSVインポート |

### 6.3 一覧レスポンス

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

- 通常一覧は `deleted_at IS NULL` のみを対象とする。
- 並び順は `occurred_at DESC, id DESC` とする。
- `pageSize` は20件で固定する。

## 7. 画面設計

### 7.1 メイン画面

```text
ヘッダー
  ├─ アプリ名
  ├─ 記録する
  ├─ 入出力
  └─ ゴミ箱 / タグ管理

操作領域
  └─ タグ絞り込み

出来事一覧
  ├─ 日時
  ├─ 本文
  ├─ タグ
  └─ 編集 / 削除

フッター領域
  └─ ページ送り
```

- 初回表示時は最新の出来事を取得する。
- 取得中はローディング状態を表示する。
- 0件時は「記録する」操作を案内する。
- APIエラー時は原因を表示し、再試行できるようにする。

### 7.2 登録・編集モーダル

- 同じコンポーネントを登録と編集で共有する。
- 登録時は本文、日時、タグを空または初期値で表示する。
- 編集時は対象データを初期値として表示する。
- 本文は必須、最大1,000文字とする。
- 保存中は二重送信を防止する。
- 保存成功後はモーダルを閉じ、一覧を再取得する。
- 保存失敗時はモーダルを閉じず、エラーを表示する。

### 7.3 削除確認

- 削除ボタン押下時に確認ダイアログを表示する。
- 確認後に `DELETE /api/lifelogs/:id` を呼び出す。
- 成功後は一覧から対象を除外し、ゴミ箱へ移動したことを通知する。

### 7.4 レスポンシブ対応

- 小さい画面では操作ボタンと一覧カードを縦方向に配置する。
- PCでは一覧の情報量を増やし、操作を横並びにできる。
- 主要操作を画面幅によって隠さない。
- カラーテーマは既存のダークモード対応を引き継ぐ。

## 8. 入出力設計

### 8.1 JSON

```json
{
  "version": 1,
  "exportedAt": "2026-09-05T14:00:00+09:00",
  "items": [
    {
      "id": "01J...",
      "body": "出来事の本文",
      "occurredAt": "2026-09-05T13:30:00+09:00",
      "timezone": "Asia/Tokyo",
      "tags": ["仕事", "読書"],
      "createdAt": "2026-09-05T13:30:00+09:00",
      "updatedAt": "2026-09-05T13:30:00+09:00"
    }
  ]
}
```

- `version` を持たせ、将来の形式変更に備える。
- `deletedAt` は通常のエクスポート対象から除外する。
- エクスポート対象は通常一覧の記録だけとし、ゴミ箱の記録は含めない。

### 8.2 CSV

- UTF-8で出力する。
- ヘッダー列は `id,body,occurred_at,timezone,tags,created_at,updated_at` とする。
- `tags` はJSON配列を文字列化して格納する（例：`["仕事","読書"]`）。
- カンマ、改行、ダブルクォートを含む値はCSV規則に従ってエスケープする。
- CSVの値をHTMLとして解釈しない。

### 8.3 インポート

- 本番ではJSONを受け付ける。CSVは開発・互換用途として扱う。
- 形式、必須値、本文長、日時、タグ名を検証する。
- 不正行がある場合は対象と理由を返し、正常な行は登録する。
- 既存データと同一と判定された行は登録しない。
- 重複判定は `id` を使用し、同じ `id` が存在する場合は既存データを優先する。

## 9. エラー・状態管理

| 状態 | UI表示 |
| --- | --- |
| 初期読み込み | スピナーと読み込み中表示 |
| 登録・更新中 | 保存中表示、二重送信防止 |
| 成功 | 成功通知、一覧再取得 |
| 入力不正 | 項目単位のエラー |
| DB接続失敗 | 利用者向け原因と再試行案内 |
| インポート部分失敗 | 成功件数・失敗件数・行別理由 |
| 削除確認 | 確認ダイアログ |
| 完全削除確認 | 復元できないことを明示 |

サーバー側では詳細なエラーをログへ記録し、クライアントには内部情報やスタックトレースを返さない。

## 10. セキュリティ・運用設計

- SQL値はプレースホルダーを使用し、文字列連結で組み立てない。
- 本文とタグはReactの通常のテキスト表示でレンダリングする。
- SQLiteファイルはGit管理対象外とし、`.gitignore` の設定を確認する。
- DBファイルのバックアップと復旧方法は、JSON/CSVエクスポートを基本候補とする。
- 本番環境ではJSONを正データとして扱い、SQLiteのDBファイルを本番データとして永続化しない。
- ゴミ箱の記録は `deleted_at` から30日経過した時点で自動完全削除する。
- 自動削除の実行方式は、定期ジョブまたはアプリ起動時のクリーンアップ処理を候補とする。
- 初期版では認証を行わないため、公開ネットワークへそのまま配置しない。
- エクスポートファイルは利用者のローカルダウンロードとして扱い、サーバーに永続保存しない。

## 12. 実装順序

1. `lib/database.ts` の接続・初期化方針を出来事用に整理する。
2. ドメイン型、入力検証、SQLiteスキーマ、Repositoryを作成する。
3. 出来事の一覧・登録・更新・論理削除APIを作成する。
4. メイン画面、一覧、登録・編集モーダルを作成する。
5. ゴミ箱、復元、完全削除、ゴミ箱を空にする操作を追加する。
6. タグ管理とタグ絞り込みを追加する。
7. JSON/CSVエクスポート・インポートを追加する。
8. テスト、lint、buildで検証する。
